## B-06 — Typeform → HubSpot opportunity → Gmail

Path: `crm/Noop_Gmail_Create_Triggered.json`
Blob SHA: `2ae3c7e6d315fe91636334a8d6069e349e8e061c`
Observed reality: despite filename, trigger is Typeform, not Gmail.

Pattern:

```text
Typeform
→ normalize answers
→ HubSpot create contact
→ IF interested
→ HubSpot lifecycle = opportunity
→ Gmail information email
```

Useful for:
- `LEAD_CAPTURE`
- `LEAD_NORMALIZE`
- `CRM_UPSERT`
- `LEAD_ROUTE/FOLLOWUP`

Strengths:
- straightforward form→CRM→conditional-response architecture;
- separates normalization from CRM calls;
- useful example of lifecycle-stage transition.

Hardening required:
- Typeform question labels are hardcoded as field keys;
- form ID is hardcoded;
- no dedupe/upsert check before HubSpot contact creation;
- direct email side effect has no idempotency key;
- interested/not-interested is a single source boolean with no configurable scoring contract;
- lifecycle stage is hardcoded;
- no ProcessRecord, ExecutionEvent, SavingsEvent, Incident or AuditEvent;
- credentials are represented by source-specific names;
- no failure compensation between contact creation, stage update and email.

Gate: INSPECTED
Priority: P0
Decision: strong pattern source for our deterministic LeadFlow baseline.

## B-07 — Simple Lead Tracker

Path: `crm/Wait_Slack_Monitor_Triggered.json`
Observed workflow name: `N_01_Simple_Lead_Tracker_Automation_v4`

Pattern:

```text
Google Forms/Sheets
→ Google Sheets Trigger
→ HubSpot
→ Slack notification
→ Gmail notification
→ Wait
→ check follow-up state
→ reminder if hot + not followed up
```

Strengths:
- very close to our commercial LeadFlow promise;
- captures lead, syncs CRM, notifies staff and reminds on stale/hot leads;
- clean example of follow-up watchdog concept.

Hardening required:
- exported workflow contains real Google Sheet IDs/URLs, Slack channel, Gmail destination and credential IDs/names;
- PII moves through Sheet, Slack, Gmail and CRM without a data-minimization policy;
- `Wait` is configured for 3 minutes while documentation describes X days — configuration/documentation drift;
- lead state is stored in spreadsheet columns instead of platform ProcessRecord/state;
- no dedupe on Sheet trigger/replay;
- no idempotent CRM upsert contract;
- notifications can duplicate on retries;
- no per-tenant configuration schema;
- no incident/telemetry/savings hooks.

Gate: INSPECTED
Priority: P0
Decision: one of the best pattern sources so far, but source configuration is too entangled for direct reuse.

## B-12 — n8n Form → appointment request → approval → Google Calendar

Path: `productivity/GoogleCalendar_Form_Create_Triggered.json`

Observed components:
- n8n Form Trigger;
- intake form + date/time selection;
- terms/acceptance step;
- receipt email;
- human approval using Gmail `sendAndWait`;
- Google Calendar event creation;
- OpenAI nodes used around request summarization/flow;
- calendar and credential IDs embedded in source export.

Strengths:
- strongest AppointmentFlow source in the current corpus;
- human approval is explicit before calendar creation;
- customer receipt and appointment summary are built into the journey;
- ignores bots at form trigger.

Hardening required:
- available date/time choices are generated locally rather than checked against real calendar availability before selection;
- approval occurs through Gmail-specific interaction rather than our ApprovalRequest contract;
- hardcoded admin email/calendar/credential identifiers;
- terms text is product-specific and must become tenant configuration;
- no slot reservation/locking → race condition if multiple requesters choose same slot;
- no idempotency for form resubmission/approval replay;
- no reschedule/cancel/reminder lifecycle;
- no ProcessRecord/ExecutionEvent/SavingsEvent/AuditEvent integration;
- PII and enquiry text need logging/AI minimization policy.

Gate: INSPECTED
Priority: P0 for AppointmentFlow
Decision: extract request → availability → approval → calendar-create lifecycle, but redesign concurrency and state ownership.

## Emerging baseline decomposition

Mining is already suggesting that LeadFlow should not be one giant workflow. The reusable pieces are converging on:

```text
LEAD_CAPTURE
→ LEAD_NORMALIZE
→ LEAD_DEDUPE
→ CRM_UPSERT
→ LEAD_SCORE/RULES
→ LEAD_ROUTE_NOTIFY
→ LEAD_FOLLOWUP_WATCHDOG
```

AppointmentFlow similarly converges on:

```text
APPOINTMENT_REQUEST
→ AVAILABILITY_CHECK
→ SLOT_RESERVATION
→ APPROVAL (optional/configurable)
→ CALENDAR_CREATE
→ CONFIRMATION
→ REMINDER
→ RESCHEDULE/CANCEL
→ POST_SERVICE_FOLLOWUP
```

These are mined patterns, not yet APPROVED_BASELINE implementations.
