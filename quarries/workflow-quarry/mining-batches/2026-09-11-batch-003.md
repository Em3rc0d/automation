### C-01 Branded AI Website Chatbot

Paths:
- `branded_website_chatbot/73_branded_website_chatbot.json`
- `branded_website_chatbot/README.md`
JSON blob SHA: `9c03e9779a7db46279bfe03079c6a75c919ea67a`
README blob SHA: `5af21b4adff78106210fe8aaa7067bcec0f2a275`

Target families:
- LeadFlow / LEAD_QUALIFY
- AppointmentFlow / AVAILABILITY_CHECK + CALENDAR_CREATE
- OpsFlow / HUMAN_HANDOFF

Observed pattern:

```text
Public website chat
→ AI agent
→ qualification / information gathering
├→ availability tool
│   → Microsoft Graph calendarView
│   → code computes free slots
├→ appointment tool
│   → POST Microsoft Graph /me/events
└→ human-handoff tool
    → Outlook email to founder
```

Strong reusable ideas:
- checks actual calendar events before proposing availability;
- separates availability and human-notification logic behind tool/subworkflow boundaries;
- fallback for enquiries not ready to book;
- documented setup + architecture canvas;
- calendar booking is a concrete business side effect rather than a toy chatbot response.

Security/production blockers before HARDENED:
- public chat trigger allows `allowedOrigins: "*"`;
- no explicit rate limit, abuse quota or tenant-aware anti-spam gate shown;
- AI tool can directly create calendar events through Microsoft Graph;
- availability check and appointment creation are not protected by a platform `BusinessAction` / optional `ApprovalRequest` boundary;
- no idempotency key around calendar creation;
- no atomic slot reservation/lock, so availability can become stale between check and create;
- business hours and timezone are hardcoded to Europe/London;
- self-workflow ID is source-instance-specific;
- personal/company wording remains embedded in prompt/tool config;
- session memory implies PII retention but no retention/minimization policy is represented;
- no `ProcessRecord`, `ExecutionEvent`, `Incident`, `AuditEvent` or `SavingsEvent` integration.

Gate: INSPECTED
Priority: P0
Decision: excellent pattern source; harden into deterministic appointment state machine with AI limited to conversation/extraction and explicit action policy.

### C-02 Cold Email Outreach Automation

Paths:
- `cold_email_outreach_automation/26_cold_email_outreach_automation.json`
- `cold_email_outreach_automation/README.md`
README blob SHA observed: `cbc83ac9eeccd7f9da876b6a41ba789a1ae482c2`

Observed pattern:

```text
Google Sheets leads
→ batch one lead at a time
→ pending-state filter
→ LLM personalization
→ Gmail first touch
→ write thread/status
→ wait
→ check same Gmail thread for reply
├→ replied → update state
└→ no reply → LLM follow-up → Gmail → update state
```

Strong reusable ideas:
- sequential lead processing;
- thread ID is retained for reply correlation;
- explicit state progression (`Pending`, `Email 1 Sent`, `Replied`, `Follow Up Sent`);
- reply/no-reply watchdog is directly relevant to LeadFlow;
- per-folder README openly documents demo shortcuts and disabled error handler.

Production blockers before HARDENED:
- lead state and orchestration truth are in Google Sheets;
- workflow starts manually rather than from our process/event contract;
- outbound AI-written emails are sent automatically;
- no opt-out/suppression/compliance policy represented;
- no sender reputation/rate-limit strategy;
- demo wait is 2 minutes rather than policy-driven delay;
- Error Trigger/Slack alert exists but is disabled;
- hardcoded Sheet ID, sender details and replyTo values;
- duplicate execution can resend outreach without platform idempotency;
- status writes can diverge from Gmail side effects on partial failure;
- no tenant-scoped ProcessRecord, telemetry, incident or savings events.

Gate: INSPECTED
Priority: P0 pattern for `LEAD_FOLLOWUP_WATCHDOG`; outbound cold outreach itself is not a default baseline until consent/compliance/business policy is explicit.

Decision: mine the state machine and reply correlation; do not inherit automatic unsolicited outreach as a universal product behavior.

### C-03 Customer Support Issue Classifier & Resolution

Paths:
- `support_issue_classifier_resolution/57_support_issue_classifier_resolution.json`
- `support_issue_classifier_resolution/README.md`
README blob SHA observed: `9a25bb0a38c8e98598c2f41e3a50911a0893778e`

Observed pattern:

```text
Daily JIRA query for stale issues
→ normalize issue + comments
→ classify state
├→ resolved
│   → sentiment
│   → feedback/autoclose/escalate
├→ waiting on customer
│   → reminder generation
└→ untouched/still waiting
    → KB agent (JIRA + Notion tools)
    → reply/escalate/close
```

Strong reusable ideas:
- domain state is classified before action selection;
- knowledge retrieval and issue search are tools rather than prompt stuffing;
- one agent path uses a Structured Output Parser;
- negative sentiment escalates rather than blindly auto-closing;
- separates stale-ticket discovery from per-ticket processing.

Production blockers before HARDENED:
- some AI-generated resolution paths can reply and close tickets without human approval;
- hardcoded JIRA status ID and Slack channel;
- source-specific close semantics may not map to every helpdesk;
- no confidence threshold/circuit breaker around classification or generated resolution;
- no tenant-level action policy;
- no idempotency for scheduled reprocessing;
- no platform audit/telemetry/savings mapping;
- KB retrieval must be tenant-isolated and citation/evidence aware before commercial use.

Gate: INSPECTED
Priority: P1
Decision: strong SupportFlow source; preserve classifier/state-machine/tool patterns, put closure/reply side effects behind policy + approval where needed.
